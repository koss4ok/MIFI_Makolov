# Задание 3. Архитектурное разъединение бизнес-логики и инфраструктуры

## Что архитектурно неудачно в текущей структуре

Проблема в том, что **правила доменной предметной области (скидки, проверки льгот, часть обработки заявок)** реализованы **прямо в контроллерах и сервисах**, которые:

- завязаны на **HTTP-слой** (механика запросов/ответов, транспортные детали);
- используют **ORM, SQL-запросы** и конкретные механизмы хранения данных;
- смешивают бизнес-правила с инфраструктурными деталями (схема БД, формат внешнего API и т.п.).

Следствие: при изменении схемы БД или внешнего API приходится менять не только технический код, но и участки **бизнес-логики**, а тестирование/поддержка становятся сложнее.

## Подходы и практики, которые уместны

### 1) Clean Architecture / Hexagonal (Ports & Adapters)

Это уместно, потому что в текущей системе бизнес-правила завязаны на HTTP/ORM/SQL. Hexagonal/Clean вводит доменное ядро и заставляет инфраструктуру работать через абстракции (порты), а не наоборот.

**Практики:**
- **Use Case / Interactor**: бизнес-сценарии (скидка, проверки льгот, обработка заявки) выделяются в отдельные кейсы, которые не знают про HTTP и не содержат SQL/ORM.
- **Порты (интерфейсы)** для данных и внешних интеграций: домен использует интерфейсы, а инфраструктура даёт реализации (ORM-репозитории, клиенты внешних API).
- **Dependency Inversion**: направления зависимостей переворачиваются так, что домен зависит от абстракций.
- **Адаптеры на границе**: контроллеры маппят входные HTTP DTO в доменные модели и вызывают use case; обратный маппинг выполняется на выходе.

### 2) Onion Architecture (слои и правила зависимостей)

Как усиление к Clean: Onion задаёт строгие правила “внутрь наружу” — доменные правила не зависят от внешнего мира.

**Практики:**
- Явное разбиение на слои: `Domain (правила)` → `Application (use cases)` → `Infrastructure (web/persistence/integrations)`.
- Контроль “утечек”: доменные сущности/правила не должны тянуть ORM-модели или детали HTTP.

### 3) DDD (упаковка бизнес-правил в доменную модель)

Так как меняются требования и нужно снижать зависимость бизнес-логики от инфраструктуры, DDD помогает сделать правила “гражданами домена”, а не фрагментами инфраструктурного кода.

**Практики:**
- **Domain Model**: выделить сущности/Value Objects и доменные сервисы для скидок и проверки льгот.
- **Policy/Rule objects**: логика расчёта скидки и проверок оформляется как самостоятельные объекты/правила.
- **Repository как порт**: доступ к данным реализуется через абстракции, а не через ORM внутри правил.

### 4) Anti-Corruption Layer (ACL) на границе с БД/внешними API

Чтобы изменения схемы БД и форматов внешних API не “размазывались” внутрь домена, полезно изолировать трансформации на границе.

**Практики:**
- Маппинг внешних DTO/записей хранения во внутренние доменные структуры выполняется в адаптерах.
- При изменениях внешнего API/ORM обновляются только мапперы/адаптеры, бизнес-правила остаются прежними.

## Итог: как это уменьшает зависимость бизнес-правил от инфраструктуры

Общий принцип такой: **контроллеры/ORM/SQL и внешние API превращаются в инфраструктурные адаптеры**, а бизнес-правила живут в домене и use cases, которые обращаются к окружению только через порты. Поэтому изменения инфраструктуры приводят к правкам на границе (адаптеры/мапперы), а не к переписыванию самой бизнес-логики.
